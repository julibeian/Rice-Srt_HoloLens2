# 动态识图（阶段 4/5）执行入口

## 目标与解释

用户 2026-10-31 提出四项任务：

1. 部署阿里云端动态模型权重；
2. 开发眼镜该项目动态识图软件；
3. 打通眼镜和阿里云链路；
4. 测试，优化。

结合根 `README.md` 的阶段表，动态阶段定义为：**在线摄影 ⇌ 双端动态交互 → 返回显示标注**。因此本轮按以下口径实施，不把单张拍照上传算作动态：

- 云端：在阿里云 ECS 上部署动态帧推理服务，沿用已验收的 ConvNeXtV2 V2 十类权重，输出类别、置信度、top3、模型版本/SHA256 与 CAM 关注区域标注；重量级权重不重复加载，动态请求走同一模型进程。
- 眼镜端：在现有稻视界应用内新增“动态识图”模式。连续从原始 PV 预览按取景框裁剪正方形低清帧，节流上传，叠加显示稳定后的类别、置信度、关注区域和端到端延迟；支持停止、断网恢复和静态拍照模式不受影响。
- 链路：眼镜 → `https://rice-srt.cn/hololens-app/api/dynamic/frame` → 本机 9013 网关 → 本机 8002 模型服务；沿用设备配对会话、图像 SHA256 与帧编号绑定。
- 测试优化：先用固定真实照片做 224/192/160/128 输入尺寸的延迟与预测一致性对照，再在真机上测端到端延迟、帧率、稳定性和异常恢复。

## 当前事实（2026-10-31）

- 阿里云轻量应用服务器：Ubuntu，2 vCPU，3.4 GiB 内存，无 GPU；`rice-disease.service`（8002）已加载 1.0 GB ConvNeXtV2 Base 权重，RSS 约 818 MB；`rice-hololens-app.service`（9013）为设备网关。
- 云端 CPU 单帧实测（无并发）：224 输入约 1.57 s，192 约 1.09 s，160 约 0.82 s，128 约 0.60 s。
- 18 张固定症状照片与 224 基线的 top1 一致性：192 为 17/18，160 为 17/18，128 为 16/18。该数字只说明输入尺寸的预测一致性，不是病害准确率。
- 真机应用当前安装 1.0.0.28 诊断+USB 中继构建（`apiOrigin=http://169.254.216.241:9021`）；生产直连包保持 `https://rice-srt.cn`。直连 443 被当前 NJAU Wi-Fi 阻断，HTTP 80 可达。
- 现有静态网关 `server.py` 负责配对、会话、图像哈希和 `/predict` 转发；模型服务 `app_v2.py` 由 `deploy.sh` 校验权重哈希后部署。

## 验收口径

- D01 云端 `/dynamic/health` 返回模型版本、权重 SHA256、输入尺寸和类别；静态 `/predict` 回归通过。
- D02 `/dynamic/analyze` 校验通道密钥、帧编号、图像 SHA256，返回与静态一致的类别字段并附带 CAM 标注和耗时；同帧号重试不重复推理；并发返回 429 而不是排队堆积。
- D03 网关 `/dynamic/frame` 只接受已配对设备会话，转发成功并返回 `capture_evidence`；401/422/429/504 均不伪造结果。
- D04 眼镜动态模式实际运行：连续取帧 ≥20 帧、显示稳定类别/置信度/关注区域/延迟，停止后恢复静态按钮；静态拍照回归通过。
- D05 真机端到端延迟与帧率有记录；根据测量调整默认输入尺寸/帧间隔/JPEG 质量。
- D06 断网、会话过期、云端 429/504 时动态模式退避并自动恢复，不阻塞应用。
- D07 云端部署带回滚证据；权重哈希、类别映射和服务健康均核对。
- D08 真实叶片、多光照和病害准确率仍不作为本轮已通过项；没有实物叶片时只用固定照片和屏幕翻拍验证链路。
