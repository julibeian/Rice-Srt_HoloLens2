## 定时精度假设与受限对照

原生只读查询得到 15.625 ms 定时间隔、QPC 19.2 MHz；本探针线程的 33 ms／66 ms 等待实际均值为 47.49／79.72 ms，接近视频的 21／12.7 fps 节奏。这仅提出调度取整的假设，没有证明门户编码线程的等待方式。

显式 45 秒测试只在本项目工作进程调用 `timeBeginPeriod(1)`，自身 33 ms 等待约 33–35 ms。实际中清稳态对照为改前 21.036、请求期间 21.536、释放后 21.102 fps，仍未达到 25。`timeEndPeriod(1)` 返回成功，查询恢复 15.625 ms，另一个只读探针的 33 ms 等待重新约 47.79 ms。相同编号只查询原测试，未重发请求。该方式没有加入功耗代理或产品默认，没有修改注册表、系统二进制或其他进程。

微软说明该 API 自 Windows 10 2004 起[不再保证影响未请求的其他进程](https://learn.microsoft.com/en-us/windows/win32/api/timeapi/nf-timeapi-timebeginperiod)。因此工作进程变精确而门户仍慢不能用来确认或排除门户自身的调度问题，也不能据此使用注入或永久全局设置。后续保留采集／编码／发送追踪与独立屏幕采集的验证路线。

`Get-DeviceTiming.ps1` 默认 Inspect 只读；PeriodTest 是显式、45 秒、成对释放的诊断。原始报告、三轮源文件和源码哈希分别保存。本轮发现回归、46 项相机／交互检查和九项读取检查通过。
