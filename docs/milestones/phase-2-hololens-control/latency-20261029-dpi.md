# 0.3.2 显示缩放修复与整套工具 CPU 对照

2026 年 10 月 29 日。已修复从 100% 切换到 125% 等显示缩放时的视频裁切，当前构建为 **0.3.2.0**。T07 继续进行；25 fps 和设备持续正常功耗仍未达标。

## 显示缩放修复

上午在真实设备窗口中，100% 普通窗口 B 点按与全屏 C 点按分别获得 trusted 事件读回。第一次全屏 C 点按因白色文字附近准星无法确认而安全拒绝，未发送选择；随后在新的具名保护内点按 C 的空白区域成功。125% 时发现窗口内容裁切，未继续真机点按。这些结果属于 0.3.1，不能当作 0.3.2 的真机回归。

下午使用不连接设备的本机测试窗口复现：100% 全屏切到 125% 后，视频控件宽 2838 像素，父容器只有 2197 像素。根因是嵌套布局没有显式定义百分比行列，DPI 自动缩放后沿用放大的首选尺寸。现已补齐布局约束，并在 DPI 变化后重新限制窗口边界；几何日志只在尺寸或 DPI 改变时记录。

修复后，真实 Windows 显示缩放为 100%、125%、150% 时，分别检查普通窗口和全屏，四个图像角区均能显示。六次真实鼠标点击均正确映射到本地 854×480 源图，最大欧氏误差约 **1.4 个源像素**。该窗口使用实际原始 BGRA 绘制路径，但不连接眼镜、不发送设备输入，也不产生真实视频帧率证据。

新增回归检查先在旧版自动缩放场景失败，修复后七组窗口缩放／自动缩放检查通过；现有指针、帧池、身份、日志与视频电源模型检查通过。电脑显示缩放已恢复原来的 **150%**，测试窗口已关闭。

**A04 尚未通过完整真机验收**：修复后的 0.3.2 还需在设备画面有效时补齐三种 DPI 下的 trusted 点按，重点是 125%。本机映射检查与此前版本的真机成功分别保留。

## 整套工具 CPU 对照

同一电脑、同一显示器、150% 全屏、Start 菜单与输入验证应用背景，旧版和 0.3.1 各测三轮、每轮约 30 秒。统计 GUI、FFmpeg、实际门户 TLS 视频传输子进程和控制台宿主的 CPU 时间；后台 USB 桥及系统网络驱动不在范围内。测试期间不发送输入，头姿有自然漂移。

| 指标 | 修复前 0.2.0 | 优化后 0.3.1 |
| --- | --- | --- |
| 合计 CPU 时间折算为单核占用 | 45.05% | 23.35% |
| 每 30 秒折算 CPU 时间 | 13.51 秒 | 7.01 秒 |
| 实际窗口绘制 | 窗口显示约 10–11 fps | 三轮均值 20.58／20.77／20.74 fps |

此场景合计 CPU 降低约 **48.2%**，达到“不高于改前”的 CPU 目标。100% 单核占用指占满一个逻辑核，并非整台 32 逻辑处理器电脑的百分比。双方采用各自产品默认清晰度和原布局：旧版高清 1280×720、12 fps 过滤与 MJPEG；0.3.1 中清 854×480、原始帧池与原生绘制，因此这是整体改动效果，不能归因于某一个优化。

CPU 结果绑定 **0.3.1 的二进制**；0.3.2 只完成上述布局与离线回归，尚未重复真实视频 CPU 测量。帧龄仍是电脑接收后的帧龄，不是相机采集到显示的总延迟。25 fps 目标保持不变。
