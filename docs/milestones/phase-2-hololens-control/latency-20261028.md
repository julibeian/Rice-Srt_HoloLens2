# 0.3.0 控制延迟修复

2026-10-28，Asia/Shanghai。本轮针对 [问题清单](../../plans/20261027-phase2-hololens-control/控制延迟与交互效率问题清单.md) 的 A–F 方案实施；二阶段整体验收继续独立登记。

## 已改动

- 默认使用 `live_med.mp4` 的 854×480 官方全息流，保留 1280×720 高清模式和按需高清单帧。实测及 [微软接口文档](https://learn.microsoft.com/en-us/windows/mixed-reality/develop/advanced-concepts/device-portal-api-reference#mixed-reality-streaming) 均表明 `live.mp4` 是高清别名，原清单将其称为中分辨率的假设已更正。
- FFmpeg 直接输出 BGRA；移除 MJPEG 编码/解码和 12 fps 限制。六槽固定帧池以引用管理位图生命周期，专用管道线程解码、后台定位，界面通过新帧通知取得最新帧、双缓冲并使用原生 DIB 缩放绘制；最多保留一个待处理通知。截图才复制一次并在后台编码，日志由独立写入线程处理。
- 本地准星立即响应鼠标。设备准星须在连续两帧中稳定可见；小步长校准拒绝文字误识别及不一致矩阵，普通点按只搜索目标附近。文字遮住准星时允许在原命中容差内调整悬停，仍只发送一次选择。
- 去掉每次操作固定 900 ms、八帧和 450 ms 等待，保留首次校准基准、当前画面检查和失败拒绝。帧龄、点击计时与租约剩余时间均使用电脑单调时钟。
- 区分等待首帧、实时、停滞、休眠与恢复失败。视频启动有 15 秒首帧预算；断流读取原设备电源状态，最多重启三次。只在具名 300 秒控制保护内发送 presence 或尝试唤醒；不定时启动业务应用。
- 协议超时后弃用原输入通道，不把迟到应答当成下一条请求结果；退出同时核对自身流关闭，并仅清理身份已核对的自身适配进程。
- .NET Framework 4.8、Windows 兼容清单与 PerMonitorV2 配置一同部署，修复 150% 缩放时窗口及顶部按钮尺寸不正确。实际鼠标坐标按当前视频显示矩形映射，不再依赖固定窗口尺寸。
- 高清抓帧真机发现第二路取流会终止交互流，已改成临时切高清、保存、切回并等待新交互帧，约 7 秒；暂停输入并清除校准。已在高清模式时直接保存新鲜帧。失败保留抓帧与恢复记录，不宣称视频无中断。

## 实测

| 指标 | 改前 | 改后 |
| --- | --- | --- |
| 后端接收/解码帧率 | 10.12–10.25 fps，源码上限 12 | 约 21 fps，无人为帧率上限 |
| 实际窗口绘制 | 后端原有上限 12；中间版本发现 GDI+ 与高频 UI 定时器使绘制低于解码 | 150% DPI 连续 736 个一秒样本，均值 20.56、P50 20.66 fps |
| 本地接收帧龄 P50 | 47.6–50.1 ms | 最终构建稳态样本 41.8–49.7 ms |
| 本地接收帧龄 P95 | 91.5–94.5 ms | 最终构建稳态样本 87.1–90.2 ms |
| 交互流带宽 | 高清约 4.4 Mbps | 中分辨率约 2.2–2.35 Mbps |
| 点按到可见选择变化 | 基线校准两次失败，不能声称存在同口径成功样本 | 最终构建独立应用 100/100 次，P50 507 ms、P95 1136 ms、最大 1267 ms |

最终构建的 100 次测试为同一独立应用中的 A/B/C 交替选择，电脑单调时钟记录请求到选择反馈区域新帧；每次保留前后画面。设备同一会话的 trusted 点击总数从 198 增至 298，目标增量 A=33、B=33、C=34，与电脑请求顺序逐次核对一致，没有据接口成功推断可见成功。实测 EXE 与测试程序已独立冻结并逐项哈希。

较早第一轮为 100 次尝试、95 次成功、5 次因准星不可见而拒绝；其原始记录保留。随后收窄搜索、加入两帧稳定确认及受限悬停调整，中途第二轮为 100/100，P50 718 ms、P95 1285 ms。日志刷新、截图锁、管道线程和恢复预算修正后，又用最终构建完成上述第三轮；三轮分别保存，不用最终成功覆盖早期失败。

CPU 为本机后端、视频取流进程与解码器合计的单核占用；场景不同会显著改变结果，不给出伪精确的降幅。恢复期间进程已替换的 CPU 样本不能用于性能比较。接收帧龄不包含设备端编码与传输前缓冲，不等同于端到端总延迟。

最终构建在同一真机三轮解码器中断后分别约 9.1、11.1、11.4 秒自动恢复，校准均失效；过期帧拒绝保持零点按。停止控制后的高清抓帧也通过，说明视频等待不依赖已经取消的输入令牌。重启/控制模式切换后的短样本出现 P95 约 727 ms，较早恢复样本曾达 2.18 秒，均保留为恢复阶段观察，不能混入稳态后声称所有时段都低于 150 ms。

为定位 25 fps 缺口，绕过桌面解码直接保存官方中分辨率流：15.029 秒收到 311 帧，按电脑实际时间为 20.69 fps；关闭稳定缓冲的诊断样本仍为 311 帧/15.049 秒。另一路官方 simulation display 为单眼 16.54 fps，未作为更快来源引入。媒体 PTS 的约 24.7 fps 和状态栏重复重绘均不能代替实际接收/绘制帧率。本机原始管道基准超过 600 fps，尚无证据表明本地管道吞吐量限制了 21 fps。

## 验证与保留项

帧完整性、部分读取、截断拒绝、池容量、并发读写、持有旧帧时替换/关闭、缩放与 DPI 坐标检查通过。新增日志检查覆盖顺序、刷新、单调时间及磁盘占用错误；原应用模型、状态只读路径、USB 发现与 46 项相机/交互回归通过。

真实 Windows 鼠标已在 144 DPI（150%）普通窗口选择 B、全屏选择 A，同一设备会话的 trusted 计数 A、B 各增加一次；截图坐标映射、实际悬停和设备事件相互对应。只证明本次两种窗口状态及两个目标，未将离线几何检查写成真实 DPI 切换。

25 fps 和 1–2 Mbps 是原清单目标，当前约 21 fps、2.2 Mbps **尚未全部达到**。不能把移除上限直接写成已达到 30 fps。四类界面各 30 次、完整 100%/125%/150% 实际 DPI 切换、深度低功耗/锁屏唤醒、真实拔插、第二台电脑和长时运行继续保持独立验收；单应用 100 次不能替代这些项目。
