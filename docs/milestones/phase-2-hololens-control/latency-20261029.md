# 0.3.1 功耗与延迟续做

2026-10-29，Asia/Shanghai。延续 [A–F 修复](latency-20261028.md)，新增用户要求：“现在唤醒，并设置接入电脑就切换正常功耗”。整体 T07 和二阶段仍未完成。

## 当前结果

原身份 USB 与门户认证重新通过。设备自然进入低功耗后，视频仅有 40 字节；具名保护内的 presence 未唤醒，官方强制跟踪入口仍返回 404，已分别关闭并恢复 Default(0)。显示/系统电源请求虽被 API 接受，实际视频仍未恢复，未将其算作唤醒成功。

发现 USB 数据在线时系统仍报告 `AcOnline=0`，原电池休眠、无人值守休眠与显示超时分别为 180/120/180 秒；此前接电分支为 0，因而没有覆盖这次连接。已加入身份绑定的 USB 功耗代理：经真实 USB 路由和原 SSH 指纹核对后，暂时把这三项 DC 超时设为 0，并保留原值；断开、停止保活或显式退出后恢复。未改接电分支、账户、配对、证书公钥、安全策略或播放静音。

设置后发送一次受控重启请求，原 USB 自动重新连回。随后读到 `LowPowerState=false`，取得有效全息视频并实际查看真实 Start 菜单边缘与应用内容。10:05、10:09 仍为正常功耗，最终代理确认序号推进，超出原 180 秒休眠期限仍保持工作。本轮没有添加每次连接都重启或反复唤醒的循环。

## 可靠性修正

- 电源查询的缺字段、不可用和请求错误统一保留为 `unknown`，不推断设备醒着，也不再因此完全跳过有限的视频恢复；身份认证失败仍阻止操作。13 项电源模型检查通过。
- 设备端以单调时钟执行 45 秒保活期限，先保存原设置再写入；异常结束保留恢复备份，后续受控启动恢复原值。使用执行请求维持代理自身运行。
- 实测发现重启前的 `active` 文件会残留。后台已改为核对不断推进的确认序号；迟滞后由原生互斥锁判定现有代理是否仍占用，再确保单实例运行。8 项恢复与竞争检查覆盖旧回执、推进、停滞、恢复、其他控制者、错误指纹、非 USB 路由和停用。
- USB 身份失联时状态明确变成未续约；不继续把历史电源回执显示为当前有效。9 项配置/帧格式/身份检查和 USB 发现回归通过。

设备端初轮 45 秒到期测试读回原值 180/120/180。最终协议 2 代理又完成显式撤销测试，三项原值逐一读回，随后重新启用并确认新代理、推进的确认序号和 DC=0。撤销保活使用了临时显示保护，设备没有因此重新进入休眠；这项测试不冒充真实物理拔插。

## 性能证据

同一 854×480 已冻结视频，直接调用改前与当前的真实帧读取方法，重复三轮。旧管线每轮读取 117 帧，新管线 241 帧；包含回放输入、解码器和读取进程的平均 CPU 时间由 1140.6 ms 降至 822.9 ms，约降低 27.9%。这证明同素材的读取/解码管线改善，未包含 GUI 和网络，不能据此直接通过整套工具的同场景 CPU 验收。

新增按实际字节位置关联视频包到达时间的诊断，区分启动与稳态。恢复后的官方中分辨率源：首包约 822 ms，排除首包后 3 秒的稳态为 **20.98 fps**，全段约 **1.31 Mbps**。改成相机透视的独立对照仍为 **21.02 fps**、2.37 Mbps，未因帧率受益而改变产品默认透视。25 fps 目标仍未达到，不能把媒体 PTS 帧率当成实际供帧。

0.3.0 的 100/100 次 trusted 点按成绩保留对应当时的冻结版本；0.3.1 的改动集中在电源观察和连接策略，不把旧测试改写成新版再次运行了 100 次。

10:27 的连接层对照使用相同场景、相同中分辨率和 20 秒限时采样：默认连接稳态 20.99 fps，单连接 TCP 即时确认成功应用后为 20.97 fps，均约 2.35 Mbps。没有帧率收益，产品默认连接保持原样。额外“每两个包确认”参数被本机 Winsock 拒绝，保留失败回执并移除这个诊断选项。没有修改系统 TCP 或网卡设置。

同时核对设备当前门户页面代码，实时预览仍只提供固定的高、中、低三档；页面未暴露其他帧率或编码配置。10:34:59 当前设备正常功耗、Default(0)，温度等级 0、所有热缓解级别 0。桌面窗口恢复为只读实时画面。它们只说明这些观察时刻和本次对照结果，不足以确定 21 fps 的根因。新增证据见 `reports/phase2-full-control/t07-transport-20261029/README.md`。
