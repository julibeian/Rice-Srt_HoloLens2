# WinML 降速定因与算法改善（2026-11-06）

以下是 2026-11-06 14:27–16:47 的已保存观察，不能代表设备当前在线。采样设备为 HOLOLENS-I0IHKJ，原 USB SSH 指纹，AC 供电，基线控制模式 Default(0)，持续 PV 新帧 896×504@30，模型输入 320，包内 YOLOv8n 六类。2026-11-06 20:02、20:31 的续查均未发现 USB 接口，SDK 候选为空；最新只读连接证据见 `connection-20261106-2031.json`。数据与复做脚本在同目录。

## 结论

1. **GPU 资源竞争是已复现的重要影响机制，跨时段降速的具体触发源仍未定因。** 正常模式下本应用的 GPU 忙时约折合墙钟时间的 32%–34%，其他工作约 64%；限时模式租约下，其他工作约 22%，本应用约 66%。同一会话推理从 1153–1214 ms 降到 543–550 ms，恢复模式后回到慢态。该模式会同时改变设备运行环境，不能视为只改变 GPU 排队的单变量操作，也不能据此把所有额外耗时归为 GPU 等待。
2. **尚不足以全面排除热与底层调度策略。** 驱动报告 GPU 频率为 342 MHz（最高 710 MHz），公开热阶段与缓解等级均为 0。温度和功耗返回零，未获得有效测量；没有内存带宽时钟和完整 CPU/GPU 队列追踪。同包重启、停载 120 秒、整机重启都未恢复；重启后空闲内存增多、推理反而变慢（1008 → 1293 ms），因此不支持“只由可用内存不足造成”的解释。
3. **算法改善有效，但幅度必须用交替对照来量。** 原版等价内容（FP32、无张量复用、无重绘去重）2221 ms，改进内容（FP16 内部权重 + 张量复用 + 不变框层不重绘）1781 ms，**已观测耗时降低 19.8%**，两臂 GPU 引擎占用同为约 98.2%。完成检测从 0.44 次/秒提升到 0.53 次/秒，增幅约 19.1%。
4. **绝对耗时跨时段漂移尚未解释，不能用不同时段的数字证明具体原因。** 相同原版内容先后约为 1.16 秒和 2.2 秒。应用停掉后测得的 GPU 占用先后约 63% 和 30%，这些是停载状态，不能代替推理期间的背景占用。`hardware/alternating63-share` 本地仅保存两个相隔约 1.08 秒的样本，本应用查询状态均为成功 0，其间忙时增量约占全引擎的 64%；该短窗口不足以代表一轮推理或 120 秒对照。窗口合成、预览渲染、模型执行及其他调度因素的贡献尚未分离。`dwm.exe` 查询错误 5 也不证明它就是负载来源。
5. **精度只能给到“同设备一致”，不能给到“与桌面参考一致”。** FP16 与桌面参考在 `bacterial_blight_0.jpg` 上有一项超过预设 0.01 置信度门槛，因此该门槛判为未通过；改做的同眼镜 FP32/FP16 对照通过：四张诊断图类别与框数一致，最大置信度差 0.007，最大框坐标差 0.249 px。真实叶片准确率仍未验收。

### 口径说明：引擎占用 96% 与本应用份额 32% 为什么不矛盾

`EnginesUtilization[0]` 是“该引擎在墙钟时间内有任务在跑的比例”，既不是本应用可用的算力，也不等于 ALU 占用。两种口径在同一次对照里同时成立：

| 模式 | 引擎占用（0 号槽） | 本应用占引擎忙时 | 推理均值 |
| --- | --- | --- | --- |
| Default(0) | 96.0%–96.5% | 32.1%–33.9% | 1138–1214 ms |
| 限时模式租约 | 87.6%–88.0% | 74.9%（单轮实测） | 543–550 ms |

这组数据说明总引擎占用不能单独预测本应用吞吐。本应用进程的 GPU 时间还包含预览、像素传递和框层渲染；它不等同于模型算子的执行时间。`Evaluate` 的墙钟耗时也包含内部调度和同步。因而不能用“进程份额 × 推理延迟”算出模型固有 GPU 时间，不能断言模型只执行 0.4 秒、其余全在等待，也不能反推后续慢态的份额。

16:33 的交替试验没有同步取得覆盖整轮的进程 GPU 时间。16:47 的两个样本只提供短窗口观察，不能补足该缺口。

## 算法改善

| 措施 | 内容 | 证据 |
| --- | --- | --- |
| 张量复用 | 复用输入/输出张量，以 `ITensorNative::GetBuffer` 读写；输入仍逐帧 Bind，保留 CPU 输出同步 | `YoloNative.c`（`YOLO_REUSE_TENSORS`）、`native-builds.json` |
| 精度 | 同一训练来源的模型内部转 FP16，输入输出仍 FP32，未重训；存在浮点舍入 | `.state/yolo-320-fp16/model-manifest.json`、`asset-checks/` |
| 重绘去重 | 帧号、新鲜度、尺寸都不变时不再整窗清屏重绘 | `src/app.js`、`lifecycle56/result.json` |

开销分解（复用生效时）：绑定 0.18–0.25 ms，输出读取 0.005–0.018 ms，后处理在 1 ms 量级；主要耗时仍在 `Evaluate`。目前无法将交替对照的组合收益进一步分配到张量复用、精度转换与重绘去重，也未单独测出三者对 GPU 调度和同步的影响。

## 限制

- 无实物叶片：真实病害检出与多光照仍未验收；本轮相机画面在四轮对照中都没有目标，因此只证明耗时，不证明准确率。
- WDDM 温度与功耗字段为 0，未获有效测量，不能据此排除所有底层策略。
- 其他 GPU 工作未归因（`dwm.exe` 访问拒绝）；跨时段绝对耗时的漂移没有找到具体来源，只能确认“同状态内比较”有效。
- 原生组件构建不逐位可复现（每次构建 PE 时间戳不同），哈希只用于核对部署文件与当次构建，不能用来判断两次构建是否同源。
- FP16 与桌面参考有一项超标，只有同设备对照通过；这是“换算一致”，不是“与原模型逐位等价”，也不是准确率结论。
- 交替对照只覆盖当前画面、当前供电与热状态，未覆盖改进版 ≥10 分钟连续运行；10 分钟长跑只有 1.0.0.57（同源内容）的记录。
